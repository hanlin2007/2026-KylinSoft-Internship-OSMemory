# OS Memory 架构设计说明（阶段 1 + 修复 + 阶段 2）

> 对应 PPT 第 8/10/14 页的概念落地。本工程以"Android 原生应用形态"模拟 OS 用户态系统服务：
> 单 `:app` 模块，包结构即分层，后续阶段可逐步升级为 Binder/AIDL 跨进程服务。

## 1.1 本地树 ↔ 云端树（阶段 1 修复，对应 PPT 第 14 页 Network Gateway / Pull）

```
                    在线/离线路由
  本地树(Local)  ────────►  NetworkMonitor(StateFlow)  ────────►  UI 状态条
   source of truth         (ConnectivityManager)
       │                                                       
       │ 单向同步 (云端可"拉取"本地)          │ 本地不能 pull 云端
       ▼                                  ▼
  TreeSyncManager  ──在线──►  CloudTreeDatabase (osmemory_cloud.db)
   (Network Gateway)         云端企业/个人库（只读展示 + 单向写入）
       │
       └── 保密隔离：policyLevel=2 / cloudEligible=false 的记忆永不外发
```

- **Local Tree**：`memory_items`（source of truth，本地优先、离线可用）。新增 `cloudEligible`（是否允许上云）、`syncState`（0 仅本地/1 待同步/2 已同步/3 同步失败）、`syncedAt`。
- **Cloud Tree**：`cloud_memory_items`，独立 `.db` 文件 `osmemory_cloud.db` 模拟云端隔离存储；仅由 TreeSyncManager 从本地树推送上来，**本地树从不从云端读回**（内网保密记忆隔离）。
- **Network Gateway**：`TreeSyncManager.sync()` 在线时把"允许上云且非敏感"的记忆推送到云端树并标记已同步；离线时返回"Cloud Tree 不可达"，本地树独立可用。
- **降级可观测**：`ModelDiagnostics` 记录每次模型调用成败与原因；流水线把 `degradeReason`（网络/HTTP 状态码/解析失败/超时）写入日志 extra；日志条目点击展开可见。

## 2. 数据模型（对应 PPT 第 9 页 Memory Item Card）

原子记忆卡 `memory_items`：

| 字段 | PPT 概念 | 说明 |
|---|---|---|
| memoId | — | 对外稳定标识（`MEMO-时间戳-随机`） |
| content | 内容 Content | 可解释自然语言，已净化 |
| title | — | LLM 抽取的一句话标题 |
| category | 封闭分类 | 画像/日程/项目/偏好/任务/关系/地点设备/其他 |
| tags | — | LLM 遴选标签，逗号分隔 |
| source / appId | 来源 Source | 来源应用与场景（控制台/记事本/对话/文件） |
| policyLevel | 权限 Policy | 0=公开 1=普通 2=敏感（安全门控输出依据） |
| createdAt/updatedAt/expiresAt | 时间 Time | 生成/更新/过期（毫秒时间戳） |
| confidence | 质量 Quality | LLM 置信度 0~1 |
| conflictState | 质量 | 0=无冲突 1=疑似冲突 2=已整合（AutoDream 阶段使用） |
| reuseCount | 质量 | 复用频率（检索命中自增） |
| evidenceRaw | 证据 Evidence | 原始片段（保留可追溯） |
| links | 连接 Links | 关联记忆/实体 JSON（阶段 2 图谱使用） |

记忆调用日志 `memory_logs`（对应 PPT 第 9 页与开发方案"日志三板块"）：
`logType ∈ {COLLECT 传入, RETRIEVE 检索, INFER 推理}`，格式化字段：时间/来源/内容摘要/标签/动作/附加 JSON。

## 3. 记忆处理流水线（对应 PPT 第 14 页 Memory Collection → Processing → Store）

```
raw_memo ──► MemoryPipeline.process()
 ① sanitize       trim / 长度校验（2~5000 字符）
 ② securityGate   敏感词栅栏命中 → policyLevel=2；LLM 敏感分类增强（失败不阻断）
 ③ extract        LLM 结构化抽取 {title, category, tags, entities, confidence}
                  └─ 网络失败降级：原文入库 + 置信度 0.3 + 日志标注"降级"
 ④ dedup          归一化文本 + 24h 同源重复 → 拒绝并记日志（reuseCount 场景）
 ⑤ store          入库 + COLLECT 日志 + INFER 日志（记录抽取过程）
```

设计要点：
- **安全门控前置**：敏感记忆在入库即打标，后续所有读取路径按 policyLevel 过滤（阶段 2 完整权限过滤，阶段 4 安全弹窗）。
- **降级优先**：任何模型调用失败都不阻断核心链路（收集/存储是硬能力，AI 增强是软能力）。
- **全链路留痕**：每条记忆的传入与推理过程都有日志，检索/画像/整合分别留日志——演示"可解释、可审计"。

## 4. 模型双通道设计

接口：`suspend fun complete(system: String, user: String, temperature: Double): String`

| 通道 | 实现 | 状态 |
|---|---|---|
| CloudModelProvider | OpenAI 兼容 `POST {base}/chat/completions`；端点自动适配 `/v1` 变体；30s 超时；健壮 JSON 提取（容忍 markdown fence、截断、字段缺失） | ✅ 阶段 1 启用（默认） |
| LocalModelProvider | 扩展点存根 | 🔲 阶段 4 可插拔 |

**本地小模型可行性结论**：Android 上部署端侧小模型完全可行，主流路线为
llama.cpp Android（llama-android）或 MLC-LLM，以 GGUF 格式跑 1~4B 级模型；
代价是 NDK 工具链 + 模型文件（数百 MB~数 GB）+ 推理速度限制。
演示环境推荐云端通道（快、稳、演示效果好）；本地通道按统一接口预留，后续热插拔无需改业务代码。

配置（`core/ModelConfig.kt`）：默认值 = PPT 调研选定的云端模型（BaseURL/Model/Key），
可被 SharedPreferences 覆盖（阶段 2 提供设置页）。
