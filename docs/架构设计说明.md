# OS Memory 架构设计说明

本文面向希望理解 OS Memory 内部设计的开发者。相比 README，这里更关注“记忆如何流动”“哪些组件负责什么”以及“当前原型与真正系统服务之间还差什么”。

## 1. 先建立整体心智模型

OS Memory 当前运行在一个 Android APK、一个应用进程中。控制台、备忘录、ChatBot 与文件分类管理器通过同进程 Kotlin API 使用同一套记忆能力。

```text
┌──────────────────────────────────────────────────────────────┐
│                    应用 / 控制台                             │
│  Console · Notes · ChatBot · File Classifier                 │
└───────────────────────────┬──────────────────────────────────┘
                            │ MemoryApiClient
                            ▼
┌──────────────────────────────────────────────────────────────┐
│                       API 门面                               │
│ 应用身份 · scope 校验 · DTO · 调用审计                       │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│                    核心记忆能力                              │
│ MemoryPipeline · SecurityGate · MemoryRetriever              │
│ SemanticReranker · ProfileBuilder · ModelDiagnostics         │
└──────────────┬───────────────────────────────┬───────────────┘
               │                               │
               │ complete()                    │ CRUD / query
               ▼                               ▼
┌───────────────────────────┐      ┌───────────────────────────┐
│        ModelProvider      │      │        Local Tree         │
│ 在线：CloudModelProvider  │      │ OSMemoryDatabase / Room   │
│ 离线：LocalModelProvider  │      │ memory_items / logs / apps│
└───────────────────────────┘      └────────────┬──────────────┘
                                                │
                                                │ eligible only
                                                ▼
                                   ┌───────────────────────────┐
                                   │     TreeSyncManager       │
                                   └────────────┬──────────────┘
                                                ▼
                                   ┌───────────────────────────┐
                                   │        Cloud Tree         │
                                   │ CloudTreeDatabase / Room  │
                                   └───────────────────────────┘
```

这个架构的核心不是“把所有数据都交给模型”，而是把**确定性的系统能力**与**AI 增强能力**分开：输入校验、权限边界、数据库和审计不依赖模型；结构化抽取、语义重排和画像生成可以使用模型增强，同时保留失败后的降级路径。

## 2. 一条记忆如何进入系统

控制台或业务应用调用写入接口后，会进入统一的 `MemoryPipeline`：

```text
raw text
   │
   ▼
sanitize
trim / 长度校验
   │
   ▼
SecurityGate
确定性规则 + 模型敏感判断
   │
   ▼
structured extraction
标题 / 类别 / 标签 / 实体 / 置信度
   │
   ▼
dedup
24 小时 · 同 source · 归一化正文
   │
   ▼
Local Tree
原子记忆卡片
   │
   ├────────► COLLECT / INFER / SECURITY 日志
   │
   └────────► 满足条件时由 TreeSyncManager 单向同步到 Cloud Tree
```

### 2.1 为什么安全门控放在前面

敏感等级不是调用应用可以任意填写的字段。系统使用确定性规则与模型判断的并集确定敏感状态；一旦被识别为敏感，记忆会进入更严格的访问和同步策略。

当前普通业务应用的读取上限固定为 `policyLevel <= 1`。`policyLevel=2` 的敏感记忆不会进入普通应用的检索上下文，也不会同步到 Cloud Tree。

### 2.2 为什么模型失败仍然允许入库

OS Memory 把“保存记忆”视为核心能力，把“AI 结构化”视为增强能力。因此模型不可用或解析失败时，写入链路可以使用确定性的降级结构继续保存，并把降级原因写入诊断与审计信息。

这使系统在云端接口异常、离线模型未准备或模型输出格式异常时，仍然能够保留输入，而不是把记忆系统本身变成一次模型调用的附属品。

## 3. 原子记忆卡片

Local Tree 的核心表是 `memory_items`。对外 API 不直接暴露 Room Entity，但理解这些字段有助于理解系统内部语义。

| 字段 | 作用 |
|---|---|
| `memoId` | 稳定记忆标识，用于更新、删除和审计关联 |
| `content` | 净化后的自然语言正文 |
| `title` | 模型抽取或降级生成的短标题 |
| `category` | 结构化类别 |
| `tags` | 可用于检索、画像和展示的标签 |
| `source` / `appId` | 记录记忆来自哪个业务入口 |
| `policyLevel` | 当前权限等级；普通应用不可读取敏感等级 |
| `createdAt` / `updatedAt` / `expiresAt` | 记忆生命周期相关时间 |
| `confidence` | 结构化结果置信度 |
| `conflictState` | 为后续冲突与整合流程预留 |
| `reuseCount` | 检索命中与复用统计 |
| `evidenceRaw` | 保留原始证据片段，便于追溯 |
| `links` | 为后续关联记忆 / 图结构预留 |

这里的“原子”强调一条记忆尽量能够独立理解和引用，而不是直接把整段聊天历史作为长期上下文保存。

## 4. 检索、重排与画像

### 4.1 `getMemo` 检索

当前检索链路分成两步：

```text
query
  │
  ├─► 权限过滤
  │
  ├─► 关键词召回
  │
  └─► semantic=true 时使用模型对候选 memoId 做语义重排
             │
             └─ 模型失败：保留关键词候选顺序并记录降级原因
```

这并不是一个向量数据库上的全库 ANN 检索。语义模型当前主要承担**候选重排**，而不是替代第一阶段召回。

### 4.2 ProfileBuilder

画像能力从 Local Tree 聚合生成用户画像、风格偏好和工作项目信息。模型可用于组织与总结；模型不可用时可以退回统计式结果，并把降级原因记录到日志。

## 5. Local Tree 与 Cloud Tree

Local / Cloud 双树是当前原型最重要的隔离实验之一。

```text
                  ┌────────────────────┐
                  │     Local Tree     │
                  │ 离线可用 / 本地源 │
                  └─────────┬──────────┘
                            │
               仅允许同步且非敏感记忆
                            │
                            ▼
                  ┌────────────────────┐
                  │  TreeSyncManager   │
                  │ Local → Cloud only │
                  └─────────┬──────────┘
                            ▼
                  ┌────────────────────┐
                  │     Cloud Tree     │
                  │ 独立 Room 数据库   │
                  └────────────────────┘
```

### 当前语义

- **Local Tree**：`OSMemoryDatabase`，是离线状态下的数据来源。
- **Cloud Tree**：`CloudTreeDatabase`，使用独立 `osmemory_cloud.db` 模拟联网 / 内网场景下的云端树；它不是远程数据库。
- **同步方向**：Local → Cloud 单向同步。
- **同步条件**：敏感记忆或用户主动标记为保密的记忆不迁移。
- **离线行为**：Cloud Tree 面板锁定，不把 Cloud Tree 内容回拉到 Local Tree。
- **业务 API**：`MemoryApiClient` 当前只访问 Local Tree，三个示例应用不直接依赖 Cloud Tree。

这一设计的重点是先验证“离线可用”和“云端隔离”的行为边界，而不是模拟一个完整的多设备云同步系统。

## 6. 在线 / 离线模型路由

所有需要语言模型的核心能力共享统一 `ModelProvider` 语义：

```kotlin
suspend fun complete(
    system: String,
    user: String,
    temperature: Double
): String
```

| 状态 | Provider | 当前实现 |
|---|---|---|
| 在线 | `CloudModelProvider` | OpenAI Chat Completions 兼容 HTTP 接口 |
| 离线 | `LocalModelProvider` | llama.cpp Android/JNI + Qwen2.5-0.5B-Instruct Q4_K_M |

每次模型调用都会根据网络状态重新选择通道。离线时不会偷偷尝试云端 HTTP 作为兜底。

需要特别注意：当前端侧 runtime 只构建 `x86_64`，正式验收范围也只覆盖“离线新增 Local Tree 记忆并完成结构化抽取”。更多细节见 [端侧模型说明](端侧模型说明.md)。

## 7. 审计与可观测性

系统记录四类日志：

| 类型 | 记录什么 |
|---|---|
| `COLLECT` | 记忆写入、更新、删除等数据流动作 |
| `RETRIEVE` | 检索、画像上下文获取、场景推荐等读取动作 |
| `INFER` | 模型抽取、重排、画像等推理动作 |
| `SECURITY` | 敏感记忆相关的入库、修改、检索命中和同步策略 |

`ModelDiagnostics` 还会记录模型调用成功或失败以及网络、HTTP、解析、超时等原因，便于区分“业务逻辑失败”和“AI 增强能力降级”。

控制台可以把当前数据与日志导出为自包含 HTML 审计快照，方便在手机浏览器中直接查看。

## 8. 三个示例应用为什么仍然有价值

虽然三个示例应用还没有跨 APK 运行，但它们已经验证了三种不同的记忆使用方式：

- **备忘录：WRITE** —— 业务对象主动关联、更新和删除记忆。
- **ChatBot：READ_WRITE** —— 检索普通记忆作为上下文，再把会话 / 项目信息写回系统。
- **文件分类管理器：READ_WRITE** —— 不读取真实文件，而是基于 Local Tree 中的记忆生成开放类别。

三者都通过 `MemoryApiClient` 使用 DTO，而不是直接访问 DAO。这为未来把传输层换成 Binder/AIDL 保留了空间。

## 9. 当前原型与真正系统服务的差距

当前已经验证的是记忆语义、模型路由、隔离策略和同进程多应用交互。要进入真正的 Android 系统服务或第三方应用生态，还需要继续补齐：

- Binder/AIDL 或其他稳定 IPC 层；
- 基于调用 UID、签名证书与用户授权的真实应用身份校验；
- API 版本协商与兼容策略；
- 硬件级密钥保护、加密数据库与更严格的敏感数据治理；
- 远程 Cloud Tree、多设备同步、冲突解决与多用户隔离；
- 更系统的图关系、向量检索、记忆整合与遗忘机制。

这些内容属于 [开发路线图](开发路线图.md)，不应被理解为当前仓库已经具备的能力。
